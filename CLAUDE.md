The integration tests (`WHALENURSE_INTEGRATION=1 go test -tags integration ./test/integration/`), `test/m0/run.sh all` and the `test/m0/m0b/` scenarios act on a real Docker daemon; the M0b steps restart the daemon, reboot or switch the image store, so only the maintainer runs them. The integration tests run in CI on GitHub-hosted runners; do not run them locally unless the maintainer has confirmed the host (see Docker host safety below).

whalenurse is a compose-aware self-healer for Docker hosts. For opted-in containers that go unhealthy or stop unexpectedly, it restarts them, then recreates them from the stack's own compose files, then (opt-in) pulls and recreates. It notifies on giving up. It is a single static Go binary that runs as a container (socket mounted) or under systemd.

## Plan v3.13 (written and approved 22 Oct 2026)

The maintainer's decisions on the code review (plan *Changes in v3.13*). Until a stack builds an item, the bullets below still describe the code as it is; these say what changes:

- **Dependents:** a sidecar made stale again by a parent whose ID or `StartedAt` changed since its last repair gets a fresh dependents-step incident at rung 0, not counted toward the flap limit (item 1, WN-002); a sidecar without its own opt-in gets manual-stop evidence (a hand stop stays stopped), and one that exited on its own is recreated with its parent (item 2, WN-028); its opt-in is decided by its persisted namespace parent, `depends_on` only when that was never learned (item 3, DQ5).
- **Drift guard:** the oracle (not the hash) runs for a reference holder on its own failure when every referenced container is current, once a compose-matrix test proves it (item 4, DQ3); rung 2's image-move allowance needs a readable `pull_policy` other than `never`/`build` (item 5, DQ4).
- **Pull rung and rollback:** a rung-2 upgrade records a *followed* move that same-image sidecars may take, and its rollback names them (item 6, DQ2/DQ6); the rollback `up` gets `--no-build` (item 7); the upgrade message gets one cuttable "the rollback does not last while heal.pull stays on" line (item 8, WN-037); after a pull that moved the image, the pause and the guard are checked again before the `up` (item 9, DQ1).
- **Labels and identity:** labels that come from the image (compared by image ID) do not steer whalenurse: an image-supplied compose identity makes the container non-compose; `whalenurse.*` on a compose container counts only if the compose file declares it; elsewhere a value equal to the image's is ignored (item 10, WN-005). The project and service labels are validated before any compose command, and `--` precedes the service once the matrix accepts it (item 11, WN-001).
- **State and health:** persisted keys are re-keyed to the current `WHALENURSE_HOST_ID` at startup (item 12, WN-010); the main loop's Docker reads have a 30 s timeout, and `/healthz` is not ok when the Docker API has failed for over 2 × `POLL_INTERVAL` (item 13, WN-027).
- **Rules and markers:** a `created` container held back by a `depends_on` condition is not started, and rule 3 reads "start, then recreate" (item 14, DQ7); reload signals (HUP, USR1, USR2, WINCH) set no marker (item 15, DQ8); after a reboot, markers older than `last_seen` − 30 s are kept (item 16, DQ10); an `on-failure` container Docker will not restore is treated like `restart: "no"` (item 17, DQ11).
- **Notifications, history, supply chain:** `Suspended`/`Unsuspended` are news again once per incident (item 18, DQ9); the drift fold applies only to the `Suspended` right after its `DriftBlocked` (item 19, WN-018); the redactor leaves boolean option values alone (item 20, WN-019); retention keeps the events of open incidents (item 21, DQ12); the syntax frontend and the BuildKit image are pinned by digest, `govulncheck` and a Go-version check gate CI and the release, and the publish job builds with an empty Go cache (item 22, WN-032/033/035).
- **Declined:** a compose staleness warning (DQ13); a dry-run state file (DQ14, documented instead) (item 23).

## Architecture (planned)

```
cmd/whalenurse/      main + subcommands (run, pause, resume, unsuspend, status)
internal/docker/     interface over github.com/moby/moby/client (events, inspect, restart, list) + fake
internal/compose/    compose binary resolution, command builder, hash/dry-run helpers
internal/engine/     incidents, ladder, flap limit (pure; injected clock; no Docker calls)
internal/rules/      inspect classification (State.Error, exit codes, heal-exited), fixture-tested
internal/store/      SQLite (modernc.org/sqlite) persistence + retention
internal/notify/     Shoutrrr wrapper, templates, dedupe, rate limit, redactor, uptime ping
internal/api/        /api/v1 JSON + SSE, /healthz, /metrics
internal/web/        read-only dashboard (html/template, embedded assets, no Node build)
internal/control/    unix-socket control server for the CLI
internal/config/     env + label parsing
```

Cross-cutting design points that span several packages:

- **Events are only triggers.**
  - Decisions come from inspecting the container after `GRACE`, because Docker event order is unreliable. `docker stop` emits `kill`, `stop`, `die` on Engine 29.9.0, and the order differs between operations and Engine versions.
  - A failed restart-policy restart emits **no event**, so the poll detects it. The poll also re-inspects containers still `restarting` after `GRACE`.
  - `health_status` events are edge-triggered, so the safety poll (default 60s) is the level-triggered backstop.
  - A startup sweep runs after `STARTUP_SETTLE`, and again after every reconnect that follows a lost events stream. The Docker API is unavailable while the daemon restores containers (API errors then mean "not ready", not an incident), and `since=` replay holds only the new daemon's last 256 events, so replay never replaces the sweep.
  - **Shutdown kills:** a daemon shutdown or reboot sends `kill` to every running container. Those kills must not set manual-stop markers or clear SUSPENDED. Mechanisms: (a) discard markers created in the 30 s before an events-stream loss, (b) persist `/proc/sys/kernel/random/boot_id` with the markers and drop them when it changes (v3.13 item 16: keep those older than `last_seen` − 30 s), (c) a restore window of `STARTUP_SETTLE` after reconnecting to a daemon that was down, in which `start` events are restores, (d) a persisted `last_seen` heartbeat: whalenurse is itself killed by a daemon shutdown (no stream loss, same boot id), so at startup the previous run's end counts as a stream loss (markers from the 30 s before `last_seen` are discarded; a gap over `POLL_INTERVAL` opens the restore window). Do **not** add a rule that recognises a burst of `kill[15]`: `docker compose stop`/`down` send the same burst, so deliberate stops would be healed.
- **One domain event stream** (`IncidentOpened`, `ActionStarted`, `ActionResult`, `Suspended`, `Recovered`, `Paused`, `TagMoved`, `Upgraded`, …). Store, notify and API/SSE all subscribe to it, so notifications and history can't disagree. Every event of a key with an open incident carries the `incident` attribute (`engine.AttrIncident`, the opening time), which notify dedupes on.
- **Notifications (M3, plan §3.12).**
  - `internal/notify` is a subscriber; `Bus.Publish` runs under the engine's lock, so `Notifier.Handle` only queues (drops and counts when full). One dispatcher renders and dedupes (the dedupe is persisted in the store's `notified` table through `notify.Ledger`; a dry run keeps it in memory); one worker and one Shoutrrr sender per URL deliver with a timeout, two retries and a per-URL rate limit. **A notification never blocks or delays healing**; failures are logged (redacted) and counted and never published onto the bus.
  - **The notification URLs and the uptime-ping URL are secrets.** Never log one, never put one in `status`, `/healthz` or an error: a URL is `#<n> <scheme>` everywhere, and every error goes through `notify.Redactor`. `config` never quotes these variables. `TestNoTokenReachesTheLogsStatusHealthzOrTheTestOutput` (`cmd/whalenurse`) greps for tokens; keep it passing and extend it when you add output.
  - Only the events in the §3.12 table are sent (`ActionResult`, `Recovered`, `Suspended`, `Unsuspended`, `TagMoved` and `Upgraded` ("upgraded during heal"), `DriftBlocked`, `DriftWarned`, `NotifyOnly`, `NeedsRecreate`, `RateLimited` (at most once an hour per URL), `RungsDisabled`, `Paused`, `Resumed`); `Suspended` with reason `drift` is folded into `DriftBlocked`, and `Suspended`/`Unsuspended` make each other news again within an incident (v3.13 items 18 and 19: once per incident; the fold only right after its `DriftBlocked`). Add a template (with a test of the worst-case length) before adding a type. Every message names the host and the container key; title ≤ 72 and body ≤ 360 runes (720 for the upgrade message, whose rollback commands are never cut).
  - **Dry-run sends notifications**, marked `[dry-run]`. `whalenurse notify test` bypasses dedupe and the rate limit.
  - The uptime ping (`WHALENURSE_HEARTBEAT_URL`) is called the "uptime ping" in code, because "heartbeat" means the persisted `last_seen` of the shutdown handling. It is skipped while the daemon is unhealthy.
- **State and control (M2a).**
  - The engine persists through an interface (`engine.Persister`), implemented by `internal/store`; it stays pure and is safe for concurrent use (one mutex), because the control socket calls it from HTTP goroutines. Events are published under that lock, so subscribers must not call back into the engine.
  - **Dry-run stores nothing** (it does not open the store or need `/data`); `run` fails fast if it cannot open the store.
  - The CLI commands (`pause`, `resume`, `unsuspend`, `status`) are served on the unix socket only. The TCP listener gets the read-only `/healthz` handler; a test in `cmd/whalenurse` asserts it has no write endpoints. Keep it that way.
  - The poll inspects every opted-in container, because only an inspect carries `RestartCount` (the crash-loop rule, §3.3 rule 3, lives in `engine.Observe`).
  - The crash-loop rule (§3.3 rule 3, `engine.Observe`) needs ≥3 `RestartCount` increases, the first ≥ `CRASHLOOP_AFTER` ago **and the latest < `CRASHLOOP_AFTER` ago**.
  - `test/m0/m0b/whalenurse-restart/` is the throwaway-VM check of the shutdown handling with whalenurse itself in a container (prepare → `sudo systemctl restart docker` → collect); only the maintainer runs the step.
- **Ladder: one pass per incident.**
  - The rungs are restart (Docker API), recreate (compose), then optional pull+recreate (rung 3, `whalenurse.heal.pull=true`; rungs 2 and 3 are unavailable together below the version gate).
  - After each rung comes a cooldown, then a re-inspect.
  - All rungs failing leads to SUSPENDED. (v3.13 item 1: a dependents-step repair after a parent change opens a fresh incident.)
  - More than `FLAP_LIMIT` incidents within `FLAP_WINDOW` also suspends, and closing an incident does not reset the flap count.
  - PAUSED is separate and expires (default 2h).
- **State key is `host/project/service/container-number`**, from compose labels, never the container ID, because a recreate changes the ID. Non-compose containers fall back to the container name and only get rung 1. The host ID is carried in every key, event and API record for the future multi-server hub.
  - **Re-keying (v3.13 item 12, built).** `cmd/whalenurse`'s `openStore` runs `store.Rekey(host, RekeyMeta)` before `Load`, in one transaction: `key_state`, `flaps`, `incidents` (open and closed), `notified` (the `key` column and the key inside the dedupe id `<type>|<key>|<discr>|<incident>`, moved with their key but never deciding a collision: the dedupe also holds pause messages keyed `host/<scope>`), the meta rows prefixed by a key (`daemon.MetaKeyed`: `parents:`) and the JSON `key` inside others (`daemon.MetaWithKey`: `tagmoved:`). **A new persisted record keyed by a state key must be added there.** On a collision, the key whose state records (`key_state`, `flaps`, `incidents`) show the later activity wins (on a tie, the current one) and the other's records are dropped. The `events` table keeps the host it was written with. A key whose remainder is not `p/s/n` or `name` is left alone. A dry run has no store and re-keys nothing. `hostIDWarning` warns at startup when the host ID is the own container's short ID; the examples set `WHALENURSE_HOST_ID`.
- **Action-in-flight window:** events for a key that whalenurse is acting on are recorded and attributed to the action, not interpreted. They must not trigger manual-stop markers, clear SUSPENDED or open an incident.
- **Rule precedence** (`internal/rules`, plan §3.3):
  - Skip rules come first: own container, `compose.oneoff=True`, swarm tasks, not opted in, PAUSED/SUSPENDED.
  - A non-empty `State.Error` means a failed start. It overrides everything else, and the exit code is never used for it. There are three shapes: a failed first start is `created` + exit 126/127/128; a failed restart-policy restart is `exited` + the previous run's exit code + `RestartCount` incremented; a failed boot-time restore is `exited` + exit 126/127/128 mapped from the error + `RestartCount` unchanged.
  - The cause splits three ways:
    - `No such container` (parent recreated): recreate the dependent.
    - `cannot join network namespace of a non running container` (parent stopped): heal the parent first, then restart the dependent.
    - "Other" causes (missing bind source, port in use, bad command): start, then recreate.
  - Then unhealthy, crash-loop, and exited handling via `whalenurse.heal-exited`.
  - Keep error-string matching in one place, backed by fixtures, because strings vary by Engine version. The port-conflict string appears as `Bind for 0.0.0.0:80` and `Bind for :::80`; match on `port is already allocated`.
  - A container whose `FinishedAt` falls in a shutdown window (30 s before `last_seen` or the stream loss, up to the restore) was stopped by the host, **whatever its exit code**, and its restart policy decides: `restart: "no"` stays down with one notification (its `network_mode` dependents stay down too), `always`/`unless-stopped`/`on-failure` are left to Docker's restore (a failed restore is rule 1), only `heal-exited=always` starts it (plan §3.3 rule 4, v3.5).
- **Heal never upgrades by accident.**
  - Every compose `up` uses `--pull never --no-build`.
  - Only the opt-in pull rung may pull, and it runs `pull --policy always <one service>` (a bare `pull` silently skips `pull_policy: never|build|missing`; plan v3.8 item 1).
  - Never use `compose down`, because it removes the shared project network.
  - The drift guard (config drift, image drift, compose version skew) runs before recreate. Any failure skips the recreate, notifies, and sets SUSPENDED. `WHALENURSE_DRIFT_GUARD=warn` overrides verified drift only (`config`, `image`); "can't verify" findings (a check that could not be made, the bundled compose's skew) still block. An upgraded host plugin is information in the drift message, not a block.
  - Config drift: the primary check is the dry-run oracle, `--dry-run --progress json up -d --no-deps --pull never --no-build <svc>`, where a `Recreate` text for the container means drift. `config --hash` is the fallback when that output can't be parsed.
  - Both are skipped for services that reference another service or container (`network_mode`/`ipc`/`pid`/`volumes_from`), because compose hashes those after resolving them. (v3.13 item 4: the oracle runs for one whose references are current.)
  - Image drift, on both image stores: compare the `com.docker.compose.image` label with what the reference resolves to for `linux/<arch>` (`docker image inspect --platform linux/<arch> --format '{{.Id}}' <ref>`, through the Engine API since the image has no CLI). **Never use `.Descriptor.digest`** (empty on the classic store, so every container would look drifted), and never `.RepoDigests` or the container's `.Image`. Plain `.Id` is never the comparator *alone*, but v3.6 also accepts it: compose before v5.5.0 writes the index ID into the label on the containerd store. `image inspect --platform` needs Engine 28.1 or later; older Engines have no fallback: rungs 2 and 3 are disabled below Engine 28.1 / Compose v5.2.0 (plan §3.6, *Minimum versions per rung*).
- **The pull rung (M4, plan §3.7, v3.8).**
  - **It needs rung 2**: `heal.pull=true` without `recreate` in `whalenurse.actions` gives one label warning and the pull stays off (`config.ParseLabels`).
  - Order: pre-action checks, **read the service's `pull_policy`** (`compose.Reader.PullPolicy`: `config --format json --no-env-resolution <svc>`, only that field is kept): `never`, `build` or an unreadable policy end the rung without running it (`engine.RungNotApplicable`: `RungUnavailable` with `not_applicable`, no rate slot, SUSPENDED with the cause "pull rung does not apply (pull_policy ...)"); then the drift guard in **image-move-allowed mode** (checks 1 and 3 only; `GuardInput.AllowImageMove`; an oracle `Recreate` is a config finding unless `config --hash` matches the label and the image moved), read the image ID (platform, and plain for the rollback), `compose pull --policy always <svc>` (replaces missing/if_not_present/none), read it again.
  - Unchanged: `engine.Result.Exhausted` suspends at once with "the pull found no newer image for <ref>". Changed: record the move **before** the `up`, non-forced `up`, a post-check that the container was replaced (`--force-recreate` otherwise), `TagMoved`, then the usual dependents step via `afterAction`.
  - **Image-only moves are let through in two more places, and only there**: rung 2 for a container with the pull rung in its ladder (`executeRecreate`: `allow := cfg.HasRung(pull)`; a recreate that ends on a different `docker.Container.ImageID` emits `Upgraded`, notified like `TagMoved`), and a stale sidecar taking the tag its parent's own pull moved in the parent's open incident (`dependentMayTakeMove`: the ref still resolves to that pull's result, the mover is a service in the sidecar's `depends_on`, the move is not older than the incident, the sidecar's `com.docker.compose.image` is the replaced image). Config drift always blocks.
  - `TagMoved` is persisted in the store's meta (`tagmoved:<normalized ref>`). A drift block names the mover (`moved_by`, `moved_at` attributes and a line of the message) only while the reference still resolves to what that pull produced.
  - The upgrade message's rollback commands (`compose.RollbackCommands`: plain old ID, the host's `docker compose`, one `up` line naming the service and the sidecars found by `sidecarsSharing`) are never cut: `MaxBodyPinned` 720 instead of 360 for a message with pinned lines. A pull `ActionResult` with an `outcome` is not notified (the giving-up and `TagMoved` messages say it).
  - Dry-run never pulls (`compose.DryRun.Pull`) but reads the policy; private registries need `WHALENURSE_REGISTRY_AUTH_DIR` (M7, below); otherwise unsupported (the compose child's `DOCKER_CONFIG` is an empty 0700 directory from `compose.PrivateConfigDir`, next to the control socket, else in the temp directory; unset it would read `$HOME/.docker`. It must be writable: compose v5.2.0 to v5.5.x create `buildx/` there in the dry-run client, and with `compose.NoDockerConfig` (the `/proc` last resort, the zero value of `ExecRunner`) their oracle fails and the guard falls back to `config --hash`; `DOCKER_AUTH_CONFIG` is removed); the loop is synchronous, so `Healthy()` tolerates an action in flight (11 min from the start of each phase: `markActing`) and `keepAlive` writes `last_seen` from a goroutine while an action runs (otherwise a daemon restart during a long pull falls outside the 5-minute shutdown window of rule 4).
  - Integration tests: a `registry:2` as a `whalenurse-test-registry-*` project; the Guard accepts only `127.0.0.1:<port>/whalenurse-test/...` for push/pull/tag, `pull --policy always <one service>` and `config --format json --no-env-resolution <one service>` from compose. Every "no pull happened" assertion has a positive control (`TestLocalRegistryRoundTrip` checks that docker events reports a pull).
- **Private registries for the pull rung (M7, plan v3.12 items 3 to 8).**
  - `WHALENURSE_REGISTRY_AUTH_DIR` is a directory whose `config.json` holds **only `auths`** with inline credentials (`auth`, `username`+`password`, `identitytoken`). `compose.LoadRegistryAuth` refuses anything else with an error that names the problem and **never a value**: another top-level key (`credsStore`, `credHelpers`, `currentContext`, `proxies`, ...), a `contexts` entry, an entry without a credential, an empty `auths`. `run` loads it first and fails on a bad file; `Compose.Pull` loads it again before every pull.
  - **Only `compose pull` gets it**, as `Command.ConfigDir` (`DOCKER_CONFIG=<dir>`); every other command keeps the private empty directory of #28 (`ExecRunner.ConfigDir`). Keep it that way: a test checks which commands carry it, and the integration `ComposeRunner` refuses it on any other.
  - **The credentials are secrets** like the notification URLs: `compose.RegistryAuth.Secrets` goes into `notify.NewRedactorWith`; never log, show or quote them. `status`, `/api/v1/status` (`pull_auth.registries`) and the home page show the registry **hosts** only, never a user name. Both secrets tests plant them and are mutation-checked; extend them when you add output.
  - The integration tests (`registry_auth_test.go`) use a `registry:2` with htpasswd (bcrypt written by the test), the positive control (no variable: the pull fails with a login error), the snapshot of the directory after a pull (compose wrote nothing), and the image with the directory mounted `:ro`.
- **Dependents (`network_mode: container:<parent>` sidecars) break whenever the parent restarts or recreates.** (M2b: they are incidents of their own, one at a time with a scheduled health wait, never a sleep. The dependents step repairs the dependents of an **opted-in** parent without an opt-in of their own, unless `whalenurse.enable=false`; their own ladder still needs one, and the step does not count toward their flap limit.)
  - **Finding the parent once its ID is gone (v3.11).** The compose `depends_on` label is **emptied by `up --no-deps`** (compose builds it from the services in scope), so after whalenurse has recreated a dependent once, the label no longer names its parent. `Daemon.parentServices` is the one resolver (the label while it has any, otherwise the set learned in `parents.go`: `parents:<key>` in the store's meta, memory only in a dry run). `learnParents` runs in `process` before the skip rules: a non-empty label replaces the set, a live `container:` reference adds its service and never shrinks it. Every reader of the label goes through it (`parentOptedIn`, `staleParentRefusal`, `sidecarsSharing`, `dependentMayTakeMove`); do not read `compose.LabelDependsOn` directly. Test fakes must drop the label on a recreate (`TestDependentIsRepairedAgainAfterComposeEmptiedItsDependsOnLabel`), or they hide this.
  - **A non-opted-in dependent's incident must still reach the engine** (`rules.Input.IncidentOpen`): a decision that needs no action passes the skip while an incident is open, otherwise the incident never recovers and the next repair suspends the sidecar unrepaired.
  - On a parent restart (same ID, parent started later), restart dependents via the API, one at a time.
  - On a parent recreate (parent ID gone), recreate the dependents with the non-forced `up -d --no-deps --pull never --no-build <dep>`. Use `--force-recreate` only if a post-check still finds a stale `NetworkMode` (M0 E1/E2).
  - **Never API-restart a dependent whose parent ID is gone.** The restart fails and turns a running-but-disconnected dependent into an exited one. It is recreated (`ActionRecreateStale`); only if compose is unavailable is it advice (`NeedsRecreate`).
  - A stale dependent stays `running` with only a loopback interface, so only the staleness sweep (or the parent's `start`/`create` event) finds it. The sweep also covers the boot-time race. At boot Docker restores a dependent after its parent, also behind a slow parent start; a parent that is not restored takes its dependents down (M0b).
  - While a parent has an open incident or an in-flight action, suppress its dependents' ladders.
  - A dependent never triggers an action on its parent.
- **Compose binary lookup order:** `WHALENURSE_COMPOSE_BIN`, then the host plugin mounted `:ro` at a fixed path, then the bundled copy. In container mode the stacks root must be mounted at the **identical path** as on the host.
- **Dashboard and API (M5, plan §3.11, v3.9):**
  - Read-only, off unless `WHALENURSE_HTTP_ADDR` is set, and built on the versioned `/api/v1` JSON API. The CLI controls the daemon over a local unix socket; there are no network-exposed write endpoints in v1. `api.Secure` serves only GET and HEAD (405 for everything else, before the token check); the control socket's paths do not exist on TCP. Tests: every method on every route, and `TestTCPHandlerHasNoWriteEndpoints`. Keep it that way.
  - **Events are persisted** (store schema 3, `events`, `AUTOINCREMENT`): the bus is seeded with `store.LastID()` and the store subscribes with `RecordEvent` (before the hub, so an event is readable when the streams wake). A dry run keeps an in-memory `engine.Ring`. A `since` above the last ID is a reset. Retention prunes events with the closed incidents; 100,000 rows at most (v3.13 item 21: never the events of an open incident, except as the cap's last resort).
  - **What leaves whalenurse is decided in `api.Service`**, for every endpoint, page and the stream: labels only `com.docker.compose.*` and `whalenurse.*` (a second filter after the daemon's own), event attributes only the allow-list `allowedAttrs` (**add a key there when you add an attribute**), every message, attribute and `State.Error` through `notify.Redactor` (it knows the HTTP token too) and length-capped. Never render env vars or full inspect output: `docker.Container` carries neither (a test plants them). `TestNoSecretReachesAnyPageEndpointOrStream` (`internal/daemon`) plants ten secrets and greps 30 responses and the SSE replay; extend it when you add output.
  - **The token** (`WHALENURSE_HTTP_TOKEN`, a secret: never log, show or quote it): bearer, or the password of HTTP Basic (a browser cannot send a bearer header on a page load or an `EventSource`); both are clear text, so TLS only (proxy or Tailscale Serve), which the docs say. SHA-256 of both sides, constant-time compare. Never from the URL. Startup warns about a non-loopback listener without a token, a token under 16 characters, and `ALLOWED_HOSTS` set together with a token (ignored).
  - **`/healthz` on the TCP listener says only `ok` / `not ok`** (`api.PublicHealthHandler`; no token, no Host check); the unix socket's `api.HealthHandler` keeps the reason for the image HEALTHCHECK and the CLI. Do not put detail in the public one.
  - **Without a token, only the Host names localhost, 127.0.0.1, [::1] and `WHALENURSE_HTTP_ALLOWED_HOSTS` are served** (403 otherwise; DNS rebinding). With a token the Host is not checked. `/healthz` is exempt.
  - **Wrong-token limiter** (`internal/api/guard.go`): 10 wrong credentials per minute per client IP (peer address; IPv6 /64; `X-Forwarded-For` is ignored on purpose), then 429 with `Retry-After`, a block of 1 min doubling to 15; while blocked even the right token gets 429. Requests with no credentials are not counted. `WHALENURSE_HTTP_TRUSTED_PROXIES` (M6, v3.10 item 5; CIDRs, empty by default, `/0` refused) makes it read `X-Forwarded-For` **only on connections from a listed peer**, taking the right-most entry that is not itself a trusted proxy; an unparsable entry or a header of proxies only falls back to the proxy's own address. Without it, behind a reverse proxy all users share the proxy's budget (documented).
  - **Skipped rungs**: `healer.skipped_rungs` comes from the open incident's `RungUnavailable` events (`incident` attribute); the pages say "skipped – not available", never a tick.
  - Headers on every response: the CSP of `api.CSP` (no inline script or style, no form: filters on the history page are links), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`. Templates must not use `style=`, `on*=` or inline `<script>`; a test greps every page.
  - `internal/web` imports `internal/api` only (a test checks) and renders `api.Service` documents. The detail page's drift status is the guard's **last verdict** from the event log, not a live check.
  - **Page rules** (plan v3.9 item 17; tests in `internal/web` and `internal/daemon/dashboard_test.go`): a link only where its page exists (`eventRows`/`incidentRows` get the set of known container keys; a Paused/Resumed row links to `/containers?scope=`; `TestEveryLinkOnEveryPageWorks` crawls every link and fails on a non-200); `api.NoiseTypes` (`EventAttributed`) are hidden by `EventsQuery.HideNoise` / `ContainerOpts(key, debug=false)`, never in the JSON API; `finalName` strips compose's `<12 hex>_` prefix in `EventDoc` and `clean`; expiries go through `expiry` ("2m left (until 14:32)"); drift text goes through `message` / `suspendedHTML` / `eventText` (plain sentence, raw text under `<details>`; the timeline's `Suspended` row is short because `DriftBlocked` explains; a pause message is reworded to "for 2h, until 19:05"); the ladder marks a blocked rung (`blockedRung`: "recreate ✗ blocked (drift)"); cards hide `td.none`; tables are cards up to 900 px (CSS: the label is absolutely positioned, the content flows: do not use grid on `td`, it scatters multi-element cells) and sit in `.tablewrap`; rollback commands are one `<pre>` each in a flex `.cmd` row with a `data-copy` button beside it (never over the text) that `app.js` wires (shown only under `.js`). Do not add inline script, style or handlers.
  - Daemon side: `daemon.view` (the last list, plus per key the last inspect and decision) is written by the loop and read by HTTP goroutines under an `RWMutex`; the loop's own `idx` stays single-goroutine. `daemon.NewAPI` wires the service; `engine.Engine.View()` is the engine's snapshot of every key.
  - `/metrics` is hand-written Prometheus text, only with `WHALENURSE_METRICS=true`, behind the token.
  - Integration test: `test/integration/dashboard_test.go` runs the image with the dashboard published on `127.0.0.1:<random port>`, with and without a token.
- The moby client (`github.com/moby/moby/client` + `/api`, not `github.com/docker/docker`) is pre-1.0, so keep it behind `internal/docker`.
- Minimum supported Docker Engine is v25, for rung 1 (restart) only. Rungs 2 and 3 (recreate, pull) and the drift guard require Engine ≥ 28.1 and Compose ≥ v5.2.0, checked at startup: below that, one warning, rungs 2 and 3 disabled, and the ladder ends with notify + SUSPENDED after rung 1. No store-guessing fallback (plan §3.6).

## Configuration surface

All env vars are prefixed `WHALENURSE_` (poll interval, grace, cooldown, flap limit, rate limit, drift guard, host ID, data dir, HTTP addr/token, metrics, the notification URLs, timeout and rate limit, the uptime ping, and others). Container labels use the `whalenurse.*` namespace (`enable`, `actions`, `heal-exited`, `heal.pull`, `cooldown`, `flap-limit`). Plan §4 holds the full tables with defaults. Update that table (and later the docs) when adding or changing a variable or label.

## Testing approach

- Engine unit tests use a fake clock and fake Docker.
- Rules are tested against scrubbed `docker inspect` fixtures, including M0 captures.
- API endpoints get golden JSON tests, which become the future hub contract.
- A test must prove env values never appear in dashboard output.
- Integration tests run in CI against real Docker, and only in `whalenurse-test-*` projects. The M3 ones send to a local webhook receiver through Shoutrrr's `generic://` service.
- The CI matrix covers the classic and containerd image stores, and compose v5.6.0 (the M0 version), the latest release, and v5.2.0 (the only release with compose bug #13878). The `image-drift` job (M0b) already runs `test/m0/m0b/image-drift.sh` on both stores.
